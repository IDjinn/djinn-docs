---
title: Numbers
---

Djinn provides fixed-width integer and floating-point types, native-width aliases, and per-type
overflow behavior via type/literal suffixes.

## Integer Types

Integers are `iN` (signed) and `uN` (unsigned) for widths 8, 16, 32, 64 and 128.

```djinn
i8 a = 127;
u32 b = 4000000000;
i64 c = 800'000'000'000;
```

Number literals support `_` and `'` separators, scientific notation (`1e9`), hex (`0xFF`) and
binary (`0b1010`) notation.

## Native-Width Types

- `nint` — signed integer with the target platform's pointer width (`i64` on 64-bit targets,
`i32` on 32-bit). Ideal for sizes, indexes and FFI with C `ptrdiff_t`/`intptr_t`.
- `nfloat` — the platform's C `float` (IEEE 754 single precision, `f32`).
- `ndouble` — the platform's C `double` (IEEE 754 double precision, `f64`).

```djinn
nint index = 0;
nfloat ratio = 1.5;
ndouble precise = 2.718281828;
```

`usize` and `isize` have a fixed width of 32 bits on every target; use `nint` for the pointer width.

Native types are display names: `typeof` and diagnostics show `nint`, and they interoperate
freely with their fixed-width equivalents (`i64`, `f32`, `f64`).

## Overflow Modes

Plain integer arithmetic is checked: when `+`, `-`, `*`, unary `-`, `++`/`--` or `/` overflows, the function throws the builtin `Overflow` error if it lists it in `throws(...)` (or has a bare `throws`), and the program stops with a report otherwise. A constant expression that overflows is a compile error. To get another behavior, give the type or the literal a suffix. Every integer type — and integer literals — accept a suffix that selects what happens when an operation overflows:

| Suffix | Mode | Behavior on overflow |
|--------|------|----------------------|
| `w` | wrapped | Two's complement wrap, like C. Hashes and random generators need it |
| `t` | trapped | Always stops the program with a report, even where `Overflow` could be thrown |
| `c` | checked | Raises the builtin `Overflow` error (requires a `throws` function) |
| `s` | saturating | Clamps the result to `MIN_VALUE`/`MAX_VALUE` |

```djinn
i32 common = 123;
i32w wrapped = 121231234w;      // wraps like C
i32t trapped = 232134324t;      // panics on overflow
i32c checked = 232343c;         // throws Overflow
i32s saturation = 23498s;       // clamps to i32.MAX_VALUE
```

The mode is a property of the operation's operands: the left operand's mode wins, and the right
one applies when the left has none. Conflicting explicit modes are a compile error.

```djinn
i32w a = 1000w;
i32w b = a + 23;      // wrapping add (mode from `a`)
i32w c = 2000w + 3w;  // wrapping add (mode from the literals)
i32s d = 2000000000s;
i32s e = d + d;       // saturates at i32.MAX_VALUE = 2147483647
```

### Status in `djinnc`

The self-hosted compiler implements `w`, `t`, `c` and `s` for `+`, `-`, `*`, unary `-`, `++`/`--` and
`/` (saturating `MIN / -1` gives `MAX_VALUE`). A conflicting pair of modes is error `E3055`.
The `c` mode throws the core `Overflow` error and needs `throws(Overflow)` or a bare `throws`;
catch it with `try ... ?: fallback` or `switch`.

Integer division and remainder by zero throw the core `DivisionByZero` error when the enclosing
function lists it in `throws(...)` (or has a bare `throws`); anywhere else the program stops with
a report. Float division by zero follows IEEE 754 (infinity or NaN), also in `constexpr`.

An explicit cast that narrows an integer stops the program when the value does not fit
(`(u8)x` with `x = 300`), and `(bool)value` accepts only `0` or `1`.

### Checked overflow

The `c` mode raises the language-level builtin `Overflow` error through the standard error
handling mechanism, so the enclosing function must declare `throws`:

```djinn
i32 safeAdd(i32c a, i32c b) throws {
    return a + b; // sets the error flag instead of wrapping
}

i32 main() throws {
    i32 result = safeAdd(2147483647c, 1c) ?: -1; // try/fallback
    return result;
}
```

### Compile-time behavior

Overflow rules also apply to literals and `constexpr`/`consteval` expressions:

- An out-of-range literal, and arithmetic on constants that overflows, is a compile error unless the literal has the `w` or `s` suffix; the message suggests them
- Saturating literals clamp at compile time (`i32s a = 3000000000s;` becomes `2147483647`)
- Wrapped literals keep the C-style truncation
- `-128` for an `i8` and `-2147483648` for an `i32` are valid: a negative literal is not an overflow

```djinn
i32 bad = 3000000000;     // error: integer literal does not fit in its type (the w suffix wraps it, the s suffix clamps it)
i32s clamped = 3000000000s; // ok: value is i32.MAX_VALUE
i32w wrapped = 3000000000w; // ok: wraps to -1294967296
```

### What is covered

The `+`, `-`, `*`, `/`, `%` operators, unary negation (`-x`) and `++`/`--` all honor the overflow
mode — including the `INT_MIN / -1` edge case for division and remainder.

### Literals

Integer literals accept decimal, hexadecimal (`0x` or `0X`) and binary (`0b` or `0B`) forms, and `_` or `'`
between digits:

```djinn
u64 all = 0xFFFF_FFFF_FFFF_FFFF;
u8 flags = 0b1010_0101;
i32 billion = 1_000_000_000;
```

A literal that does not fit its type is a compile error in every base.

## IEEE 754

`f32` and `f64` are the IEEE 754 `binary32` and `binary64` formats. Which revision of the standard the
generated code follows is a compiler setting; the default is the newest one,
[IEEE 754-2019](https://standards.ieee.org/ieee/754/6210/).

| Setting | Command line | `djinn.proj` (under `compiler:`) |
| --- | --- | --- |
| Revision | `--ieee754=2019\|2008\|1985\|none` | `ieee754: "2019"` |
| Environment | `--fp-env=default\|strict` | `fp-env: "default"` |

Command-line options win over `djinn.proj`.

### Revisions

Every conforming revision gives the same results for `+`, `-`, `*`, `/`, `%`, comparisons and conversions:
correctly rounded results, subnormal numbers (gradual underflow), signed zeros, infinities and NaN. A
multiplication followed by an addition is never fused behind your back: `a * b + c` always rounds twice.
The revisions differ in which operations exist:

| Operation | 1985 | 2008 | 2019 |
| --- | --- | --- | --- |
| `a.fma(b, c)` — `a * b + c` with a single rounding | error E3056 | `fusedMultiplyAdd` | `fusedMultiplyAdd` |
| `a.min(b)` / `a.max(b)` | `a < b ? a : b` | `minNum` / `maxNum` (NaN ignored) | `minimumNumber` / `maximumNumber` |
| `a.minimum(b)` / `a.maximum(b)` — NaN propagates, `-0 < +0` | error E3056 | error E3056 | yes |
| `a.minimum_number(b)` / `a.maximum_number(b)` — NaN ignored, `-0 < +0` | error E3056 | error E3056 | yes |

These methods exist on every `f32` and `f64` without importing anything; a method with the same name in
an `impl f64 { ... }` block takes precedence.

```djinn
f64 nan = 0.0 / zero;
f64 a = nan.min(1.0);      // 1.0: minimumNumber ignores the NaN
f64 b = nan.minimum(1.0);  // NaN: minimum propagates it
f64 tenth = 0.1;
f64 c = tenth.fma(10.0, -1.0); // 5.55e-17, while tenth * 10.0 - 1.0 is exactly 0.0
```

`--ieee754=none` gives up conformance for speed: every float operation gets LLVM's fast-math flags
(reassociation, contraction into `fma`, no NaN, no infinities, no signed zeros) and subnormals may be
flushed to zero. Results can change with the optimization level and the target.

### Floating-point environment

With `--fp-env=default` the compiler assumes round-to-nearest-even and that nobody reads the exception
flags, so it may fold `1.0 / 3.0` at compile time or delete a division whose result is unused.

`--fp-env=strict` gives the program the dynamic attributes of IEEE 754 (rounding direction, clause 4) and
its status flags (clause 7): every operation uses the rounding mode set at run time and keeps its
exceptions observable. The generated code uses LLVM's `llvm.experimental.constrained.*` operations and
the `strictfp` attribute; `<`, `<=`, `>` and `>=` are signaling comparisons and `==`/`!=` are quiet.

```djinn
extern "C" {
    i32 fesetround(i32 mode);
    i32 fetestexcept(i32 flags);
}

fesetround(FE_UPWARD);     // platform constant: 0x200 on Windows, 0x800 on x86-64 Linux
f64 third = one / three;   // rounded upward
```

`strict` needs a conforming revision; `--ieee754=none --fp-env=strict` is rejected.

In the conforming revisions the basic operations (`+`, `-`, `*`, `/`, `%`, `fma`, `min`/`max`, conversions)
give bit-for-bit identical results on every target, because contraction and reassociation are forbidden
and each operation rounds exactly as the standard says. Library functions such as `sin` or `pow` come
from the platform's C library and are not covered by this guarantee.

## Non-Zero Types

The `n` suffix declares an integer type that cannot hold the value `0`. The domain of `iNn` is
`MIN..-1` plus `1..MAX`; the domain of `uNn` is `1..MAX`. Non-zero types compile to the same
representation as their base type — the guarantee is enforced by the compiler:

- Assigning the literal `0` (including `0x0`, `0b0`) is a compile error
- Implicit conversion from a plain integer type is rejected — the value might be zero; use an
explicit cast, which is trusted and unchecked at runtime
- Non-zero values convert implicitly to the plain type
- Arithmetic results lose the guarantee (`a - a` is zero), so `i32n + i32n` produces `i32`
- `++`/`--` are rejected on non-zero variables (the result may be zero), and a non-zero
variable must be initialized when declared

```djinn
u32n divisor = 10;        // ok
u32n bad = 0;             // error: integer literal 0 is not assignable to non-zero type 'u32n'

i32 plain = 5;
i32n fromPlain = plain;   // error: cannot implicitly convert 'i32' to 'i32n'
i32n trusted = (i32n)plain; // ok: explicit cast is trusted

i32n a = 5;
i32 sum = a + a;          // ok: result type is i32 (non-zero-ness dropped)
i32 back = a;             // ok: non-zero flows into the plain type freely
```

The suffix combines with overflow suffixes in either order: `i32nt`/`i32tn` is a trapped
non-zero 32-bit signed integer.

### Contracts

Non-zero types integrate with the contracts system in both directions:

- **Non-zero parameters are implicit `require(p != 0)` clauses.** The callee checks the
parameter at entry (a violation throws `ContractViolation`), and with compile-time error
enforcement a call passing a constant `0` is rejected by the compiler (`9007`). Inside the
body the parameter carries the guarantee, so divisions by it skip the zero-divisor check.
- **`require(p != 0)` upgrades a plain parameter** to non-zero for the whole body: it can be
assigned to `i32n` variables and used as a proven non-zero divisor. The explicit require is
folded into the single non-zero entry check.
- **`ensure(return != 0)` upgrades the return type** to non-zero for callers, regardless of
declaration order, so `i32n x = try f() ?: 1;` compiles (functions with contracts are
throwing, hence the `try`).

```djinn
i32 safeDiv(i32n b) {
    return 100 / b;   // no zero-divisor check: b is contract-guaranteed non-zero
}

i32 legacyDiv(i32 b)
    require(b != 0)   // b is treated as i32n inside the body
{
    return 100 / b;
}

i32 five()
    ensure(return != 0)
{
    return 5;
}

i32 main() {
    i32n x = try five() ?: 1;  // ok: ensure proves the result non-zero
    safeDiv(0);       // compile error: passes zero to non-zero parameter 'b'
    return 0;
}
```

Division and remainder by a proven non-zero divisor (non-zero literal, `i32n` variable,
contract-proven parameter, or a cast to a non-zero type) emit a plain `sdiv`/`srem` with no
runtime zero check.


## Booleans

`bool` occupies one byte in memory and only holds `0` or `1`. `&&` and `||` short-circuit; `&`, `|` and `^` always evaluate both sides. Booleans have `==` and `!=`, but no arithmetic and no ordering: `a < b` between two bools is a compile error.

## Disabling an operator

An operator declared without a body inside an `impl` (or a struct) is disabled: using it is a compile error. A type with no declaration for an operator keeps the built-in behavior.

```djinn
impl bool {
    operator <(bool left, bool right) -> bool;
    operator >(bool left, bool right) -> bool;
}

struct Id {
    i32 value;
    operator <(Id left, Id right) -> bool;   // error: operator '<' is disabled for 'Id'
}
```

In an `interface` the same form still means "implementers must provide this operator".
