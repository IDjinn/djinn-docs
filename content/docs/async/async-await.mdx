## Overview

Djinn supports `async` functions and `await` expressions for writing asynchronous code. Under the hood, async functions compile to LLVM coroutines that are
fully optimized by the backend — in many cases resulting in **zero overhead** after inlining and coroutine elision.

```djinn
async i32 compute(i32 x) {
    return x * 2 + 1;
}

async i32 main() {
    i32 result = await compute(10);
    printf("result: %d\n", result);  // result: 21
    return 0;
}
```

## Async Functions

Any function can be marked `async` by adding the keyword before the return type. An async function returns a **coroutine handle** (`ptr`) instead of its declared return type.

```djinn
async i32 fetch_value() {
    return 42;
}
```

The caller uses `await` to obtain the actual return value.

### Syntax

```
async <return_type> <name>(<params>) { <body> }
```

## Await Expressions

The `await` keyword suspends the caller until the async function completes, then extracts the return value from the coroutine promise.

```djinn
i32 result = await some_async_function(args);
```

### Where you can use await

- Inside `async` functions (chained coroutines)
- Inside regular `main()` or any function (the compiler generates an await loop)

### Multiple awaits

You can await multiple async calls sequentially:

```djinn
async i32 add(i32 a, i32 b) {
    return a + b;
}

async i32 square(i32 x) {
    return x * x;
}

async i32 main() {
    i32 a = await square(3);    // 9
    i32 b = await square(4);    // 16
    i32 sum = await add(a, b);  // 25
    return sum;
}
```

## Chaining

Async functions can call and await other async functions, creating chains of coroutines:

```djinn
async i32 step1(i32 x) {
    return x + 10;
}

async i32 step2(i32 x) {
    i32 val = await step1(x);
    return val * 2;
}

async i32 pipeline(i32 x) {
    i32 val = await step2(x);
    return val + 5;
}

// pipeline(5) -> step2(5) -> step1(5) = 15 -> 30 -> 35
```

## Async functions that never suspend

An `async` function only needs a coroutine when it can actually suspend. The compiler checks every async function and
compiles it as a plain synchronous function when its body has no suspension point:

- no `std::builtin::coro.suspend()` or `coro.handle()`, and no runtime async I/O call (`Console`, `Socket`,
  `std::filesystem`, `Task.delay`...);
- no `spawn`;
- every `await` is a direct call to a function that never suspends either. This is decided over the whole call graph,
  so a chain of such functions is converted together.

`await f()` on a converted function becomes an ordinary call: no coroutine frame is allocated and the scheduler is not
involved. The result and the errors of a `throws` function reach the caller exactly as through the task. The compiler
reports warning `E6004` on the function, because `async` has no effect there:

```djinn
async i32 leaf(i32 x) {      // warning E6004: 'async' has no effect, compiled as a synchronous function
    return x + 1;
}

async i32 middle(i32 x) {    // warning E6004: it only awaits 'leaf'
    i32 value = await leaf(x);
    return value * 2;
}

async i32 waits(i32 x) {     // stays async: Task.delay suspends
    await Task.delay(10);
    return await leaf(x);    // a direct call
}
```

### Tail-recursive cycles

A recursion is converted when it can run in constant stack: every call from one member of the cycle to another is
`return await g(...)`, so codegen turns it into a guaranteed tail call (LLVM `musttail`) and no level stays on the
stack. The whole cycle is converted or none of it, and only when all of these hold:

- no member suspends (the same rules as above) and every other `await` targets a function that never suspends;
- every call inside the cycle is `return await g(...)` with exactly the same signature: return type, `throws` list and
  parameter types;
- every parameter and the return type is a scalar (integer, float, `char` or `bool`) of at most 64 bits, so every value
  travels in registers: no argument can point into the frame that the tail call replaces, and no result comes back
  through a hidden pointer, which LLVM cannot tail call;
- a `throws` member lists its errors explicitly (not `throws` alone), and each error is a plain struct of at most two
  such scalars without a custom `[Align]`, so the result record also fits in registers;
- no member has a parameter or local that needs a `destroy()` / `Disposable` cleanup, which would have to run after the
  call;
- the cycle has a base case: at least one `return` that does not continue into the cycle.

```djinn
async bool is_even(i32 n) {   // converted together with is_odd, no warning
    if (n == 0) {
        return true;
    }
    return await is_odd(n - 1);
}

async bool is_odd(i32 n) {
    if (n == 0) {
        return false;
    }
    return await is_even(n - 1);
}

async i32 depth(i32 n) {      // stays async: the await is not the last thing it does
    if (n == 0) {
        return 0;
    }
    i32 below = await depth(n - 1);
    return below + 1;
}
```

A converted cycle gets no `E6004`: without `async` its calls would be plain recursion, with no guaranteed tail calls.
The levels of a converted cycle do not appear in a panic's stack trace, since each tail call replaces its caller's
frame. `is_even(1000000)` runs in about the time of a loop instead of allocating a million coroutine frames.

Converting removes the scheduler round trip of each await, so a converted call runs to completion before any other
ready task, while an await of a coroutine lets ready tasks (for example spawned ones) run first. In a synchronous
function, an await of a converted function does not run the event loop either: tasks spawned earlier only run at the
next await that really waits on a coroutine.

The conversion does not depend on the optimization level: `-O0`, `-O2` and `--run` behave the same. Pass
`--no-async-elision` to keep every `async` function a coroutine (no conversion and no `E6004`).

## Async Main

When `main` is declared as `async`, the compiler automatically generates:

1. `__djinn_async_main()` — the actual coroutine with your code
2. `main()` — a synchronous wrapper that calls and awaits the async entry point

```djinn
// You write:
async i32 main() {
    i32 val = await compute(10);
    return val;
}

// Compiler generates (conceptual):
// ptr __djinn_async_main() { ... coroutine body ... }
// i32 main() { hdl = __djinn_async_main(); await hdl; return result; }
```

## Frame Memory

Coroutines are stackless, as in C++20: the only state that outlives a suspension is the coroutine frame, which holds the
locals that live across an `await`. When CoroElide cannot place the frame in the caller, it comes from
`__djinn_coro_alloc(size)` and goes back through `__djinn_coro_free(frame, size)`. The runtime keeps freed frames in
size classes of 64 bytes (up to 2 KiB, 64 frames per class) and hands them out again, so a program that keeps awaiting
reuses the same few frames instead of calling `malloc` for each call. Larger frames go straight to `malloc`/`free`.

The scheduler itself does not allocate per operation: the ready queue is a ring buffer and the "who is waiting on whom"
state (the continuation of an awaited coroutine and the waiting flag) lives in an open-addressing table keyed by the
coroutine handle. Both grow by doubling, so an `await` costs no allocation once they reach their working size, and there
is no limit on how many coroutines wait at the same time.

## Implementation Details

Each `async` function generates the following LLVM IR structure:

```
entry:
  %promise = alloca <return_type>
  %id      = call token @llvm.coro.id(...)
  %alloc   = call i1 @llvm.coro.alloc(token %id)
  br i1 %alloc, label %coro.alloc, label %coro.begin

coro.alloc:
  %size = call i64 @llvm.coro.size.i64()
  %mem  = call ptr @__djinn_coro_alloc(i64 %size)
  br label %coro.begin

coro.begin:
  %hdl = call ptr @llvm.coro.begin(token %id, ptr %mem)
  ; ... function body ...
  store <result>, ptr %promise
  br label %coro.final

coro.final:
  call i8 @llvm.coro.suspend(token none, i1 true)
  ; switch → cleanup or trap

coro.cleanup:
  %free.mem = call ptr @llvm.coro.free(token %id, ptr %hdl)
  call void @__djinn_coro_free(ptr %free.mem, i64 %size)

coro.suspend:
  call void @llvm.coro.end(ptr %hdl, ...)
  ret ptr %hdl
```

The `await` expression generates:

```
await.loop:
  %done = call i1 @llvm.coro.done(ptr %handle)
  br i1 %done, label %await.ready, label %await.resume

await.resume:
  call void @llvm.coro.resume(ptr %handle)
  br label %await.loop

await.ready:
  %promise = call ptr @llvm.coro.promise(ptr %handle, ...)
  %result  = load <type>, ptr %promise
  call void @llvm.coro.destroy(ptr %handle)
```

Functions are marked with the `presplitcoroutine` attribute so the LLVM coroutine passes can process them.

## task{'<T>'}

The `task<T>` struct in `std::sys` represents a handle to an async coroutine. It wraps a raw coroutine handle and provides methods to check completion, resume execution, and retrieve results.

```djinn
import std::sys;

struct task<T> {
    void* handle;
}
```

### Constructor

```djinn
task<i32> t = task<i32>(some_handle);
```

### Coroutine Primitives

The low-level `coro` struct in `std::builtin` provides direct access to LLVM coroutine intrinsics:

```djinn
import std::builtin;

struct coro {
    static void* handle();     // get current coroutine handle
    static bool done(void* h); // check if coroutine is done
    static void resume(void* h);
    static void destroy(void* h);
    static void suspend();     // suspend current coroutine
}
```

These primitives are used internally by `Socket`, `Console`, and other async APIs to implement cooperative scheduling with the Djinn runtime's event loop.
